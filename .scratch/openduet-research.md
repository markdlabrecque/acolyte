## Bottom line

OpenDuet is an implemented proactive assistant, not merely a proposal. It combines OpenBot's server, UI, tool governance, Docker computers, scheduled work, event triggers and multi-agent machinery with an OpenDuet tenant configuration and assistant-specific Tasks, Make, onboarding, triage and briefs. Its README explicitly calls it early development. Its storage and queues are real, but they are **not a general guarantee of checkpointed, exactly-once agent execution**. In particular, an accepted routine can be lost mid-turn, some task turns are retried, and interrupted event-driven work is deliberately failed rather than replayed. [README](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#features-and-capabilities), [routine dispatch](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L59-L69), [event recovery](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/responsibilities/store.ts#L333-L347).

The application is self-hostable and MIT-licensed. The supported OpenDuet setup nevertheless requires CopilotKit Intelligence plus model access. Managed Intelligence has a free allowance, not unlimited free production use. Fully local Intelligence is a licensed evaluation or a separately licensed production deployment. There is **no mandatory rented E2B/Daytona-style sandbox in the documented quick start**: the computers are local Docker containers. [Quick start](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#quick-start), [Compose](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docker-compose.yml#L82-L124), [official Intelligence pricing](https://www.copilotkit.ai/pricing).

## Architecture and execution

- OpenBot supplies a React/Vite app on 3010, Hono API and CopilotKit runtime on 3001, PostgreSQL with pgvector on 5432, AG-UI agent endpoints, and agent-computer containers with Chromium, files and shell. Intelligence supplies durable threads, memory facilities and realtime transport. The supervisor creates and manages per-Bot computers. Default local startup uses Docker for Postgres, computers and sample/framework agents, then host Bun processes for API, worker and app. [Architecture](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#services-and-ports).
- OpenDuet's package is `openbot/examples/openduet`, with brand, agents, channels, model and skills. The main OpenDuet agent is `built-in`, not itself a mandatory remote LangGraph deployment. Additional AG-UI agents and a selected framework harness can be registered. [Actual agents](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/examples/openduet/agents.yaml#L1-L13), [additional agents](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/examples/openduet/agents.yaml#L116-L140).
- Governed tool calls return to the API gateway, which checks grants/current policy, records an audit decision, then forwards permitted work. Custom/unknown MCP tools count as writes unless positively classified as reads. Deny rules take precedence. Important default: the platform's explicit initial computer policy is `allow: ["true"]`, not a strict deny-by-default deployment configuration. Approvals add another control layer. [Governance and defaults](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#browser-action-governance).
- Browser use has live screen and human takeover for login, 2FA and CAPTCHA. Secrets use masked entry rather than ordinary chat, and stored credentials are encrypted and write-only through the API. These are implemented controls, not proof that every possible generated shell/network action is safe. [Control and secrets](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#human-control-and-secrets).

## Persistence, restart and retry semantics

### What is persisted

PostgreSQL stores product state, policy, grants, audit, credentials, agent profiles, mappings, routines, work items and task/event ledgers. Intelligence owns durable conversation threads. Each Docker computer has persistent workspace and browser-profile volumes; ordinary stop preserves them. These persistence domains need separate backup/recovery consideration. In-browser Activity is explicitly ephemeral and disappears on reload; the server audit trail is the lasting record. [Architecture](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#watching-a-bot-work), [startup/stop behavior](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#quick-start).

### Shared queue

`work_items` is a durable Postgres queue with idempotent `(kind, key)` offers, transactional `FOR UPDATE SKIP LOCKED` claims, database-clock leases, renewal and retry counts. The default claim cap is five, though individual work kinds override it. Expired leases make unfinished work available again. Source explicitly warns that attempt greater than one can mean prior effects or spending already occurred. Queue deduplication is not external-effect deduplication. [Queue implementation](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/work/queue.ts#L1-L110).

### Routine firings

- Each due minute has a stable routine/minute key; enqueue happens before compare-and-set advancement of the next-run clock. A crash between those steps can re-offer the same key safely. [Offer path](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L172-L213).
- Dispatch leases are 60 seconds, dispatch retries wait 60 seconds, and the default lateness grace is ten minutes. Dispatch uses the queue attempt cap. The local worker polls every 30 seconds and bounds its internal HTTP dispatch to 30 seconds. [Constants](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L30-L69), [worker](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/worker/src/index.ts#L64-L99).
- Crucial limitation: the queue item is finished when the API accepts dispatch with 202, **before the agent turn completes**. Server death after acceptance leaves an abandoned run, which a later sweep marks failed. It does not resume that computation. The reaper threshold is twice the headless-turn timeout, currently ten minutes. [Abandoned-run handling](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L59-L69), [reaper](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L295-L322).
- A timed-out dispatch may already have been accepted. Another dispatch attempt opens another run ID; a lost lease after acceptance can also cause redelivery. The code explicitly logs `routine-fire-redelivery-possible`. Do not interpret the stable queue offer key as an exactly-once execution guarantee. [Dispatch uncertainty](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L414-L459).
- Actual turn failure is final for that occurrence, distinct from dispatch retry. A routine announces the first failure after success, disables after ten consecutive failures and announces that. [Fatigue semantics](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/routines.md#the-fatigue-rule).

### Tasks, event work and approvals differ

- Started Tasks have two allowed turn runs, a three-minute lease and ten-second retry delay. Executable `drainTask` retries thrown failures up to `TASK_RUNS`, and expired leases permit crash recovery. There is an older adjacent comment suggesting errors are final; use the live `TASK_RUNS`/`drainTask` path rather than that comment as the current contract. Approval/question suspension is handled as a successful stop, not a turn error to repeat. [Constants](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/engine.ts#L82-L107), [task drain](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/engine.ts#L800-L838). This is turn retry, not demonstrated transactional rollback of arbitrary tools.
- Event-driven Responsibilities commit event, run and queue entry in one transaction. A recovered run already marked `running` is failed with the explicit explanation that actions may already have executed and it was not replayed. This is a deliberate uncertainty boundary. [Ingress contract](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/responsibilities/triggers.ts#L1-L12), [recovery code](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/responsibilities/store.ts#L293-L347). Engine claims at most two attempts; normal exceptions settle failed, while approval/input suspension settles waiting. [Engine](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/responsibilities/engine.ts#L32-L172).
- Approvals retain an action digest, continuation, decision and result. Completed stored results can be replayed without acting again; an approval is atomically consumed before execution and cannot simply authorize a second action. A consumed approval with no saved result is refused as already used/revoked rather than blindly executed again. This is useful action-level protection, not atomicity between PostgreSQL and a remote vendor. [Approval execution gate](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/approvals/service.ts#L482-L545).
- Bot-to-Bot handoffs are durable queued work with renewed leases and explicit terminal failure reporting. That is stronger than an in-memory callback but still not evidence that every external effect of a handed-off turn is exactly once. [Handoff design](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#one-bot-handing-work-to-another).

## Triggers, schedules and autonomous operation

These are implemented, but are different mechanisms with different permissions and delivery rules.

1. **Routines** are conversationally created five-field cron schedules with timezone support, running as their creator using that person's grants/accounts and posting into a channel. Minimum frequency is every 15 minutes; at most 20 enabled routines per person. A separate worker is required and the UI reports missing/stale worker check-ins. Older missed windows are skipped, not replayed or combined into a reminder catch-up digest. Current source jumps a stale clock directly forward from now; the prose guide's older occurrence-by-occurrence description is stale. [Routine guide](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/routines.md), [timezone/default UTC](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/store.ts#L550-L560), [current missed-window code](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/routines/sweep.ts#L172-L220).
2. **Proactive research** periodically reads connected apps, forms candidate memories and suggests tasks. Default interval is 240 minutes, configurable from 15 to 1,440 minutes. Limits are five suggestions and ten memories per run. Research is enforced read-only for connected apps; it cannot drive the computer/browser, write externally, message a peer or ask a person through coordination. Its follow-on check-in can only offer task cards. The owner starts the proposed work. This is autonomous discovery, not unrestricted autonomous execution of suggestions. [Settings](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/types.ts#L6-L29), [enforced boundary](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/restriction.ts#L1-L75), [engine intent](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/engine.ts#L2-L22).
3. **Tasks** requested by the owner run headlessly in their own conversations, can use their granted tools while the browser UI is closed, and stop for approvals/input. The main Chat gets a card instead of owning the whole long-running interaction. [Task instructions and routing](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/examples/openduet/agents.yaml#L83-L109), [task engine](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/engine.ts#L800-L838).
4. **Responsibilities/event triggers** support generic webhooks, GitHub, Linear, Sentry, PagerDuty, inbound email and Slack. Filters include event type and one dotted-field equality; GitHub can pin a repository. Slack trigger modes include mention, phrase, reaction and message with workspace/channel filters. Vendor ingress authenticates signatures. Email requires configured Amazon SES receiving/SNS infrastructure; setting up a Gmail account alone does not provide this ingress. [Trigger schemas](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/responsibilities/triggers.ts#L32-L183), [email infrastructure](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L563-L570).
5. **Self-scheduled follow-ups** let a Bot schedule a one-shot future turn with a reason, at least one minute and at most seven days away. Limits are five pending and 20 scheduled per rolling day per person/Bot. They use durable `bot.wakeup` work items, with normal tools, governance and approval behavior. The source's statement that caps prevent a loop should not be read literally as preventing all recurring chains: it bounds pending work and scheduling rate. [Wake-up implementation](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/agents/wake-up.ts#L1-L38), [transactional caps](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/agents/wake-up.ts#L181-L210).
6. **Morning brief** is currently triggered by opening Chat on a later day, not inherently an always-on 09:00 push alarm. Its claim and job are committed together, and delivery continues if that opening browser leaves. It is keyed to conversation/local date and retries once like a task. A separately configured routine can provide timed work. [Current README wording](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#features-and-capabilities), [opening drain](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/proactive/engine.ts#L840-L915).

API-side proactive and follow-up sweeps are running code, not just exported modules. Proactive polling is every minute and wake-up polling every five seconds; the routine worker is separate. Headless turns currently have a five-minute timeout, five-second abort backstop and renewable Intelligence thread lease. [Sweep wiring](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/index.ts#L2272-L2338), [turn limits](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/toolkit/src/limits.ts#L8-L43).

## Multi-agent support

Multiple durable Bot profiles, built-in or remote endpoints, per-Bot role descriptions, visibility, grants and computers are implemented. Group conversations maintain a shared attributed transcript but separate Intelligence threads per Bot because an Intelligence thread has one agent. `message_bot` is a granted, typed handoff carrying task/constraints/success criteria, with server-bound actor, target, destination and chain depth. Depth and per-run fanout have explicit caps. `ask_person` provides escalation. Plain handoff answers land in the recipient Bot's own conversation; group conversation routing has its own shared transcript behavior. This is real delegation and group support, not only multiple independent chat tabs. [Profiles](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/coworkers.md), [groups](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#coworkers-and-channels), [handoffs/caps](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#one-bot-handing-work-to-another).

## Filesystem, shell and browser

- The default "computer" is a Docker container, not unrestricted access to the user's home directory. It has Chromium, a persistent `/workspace`, browser profiles and shell/file tools. Per-Bot mode gives separate containers/volumes; shared mode deliberately shares the computer. Ordinary containers share the host kernel; gVisor via `COMPUTER_RUNTIME=runsc` is optional. Supervisor holds the Docker socket and must stay private. [Computer architecture](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#computers).
- Browser and shell traffic use a policy proxy. The documentation explicitly warns that a program opening raw sockets can ignore proxy environment variables; cluster NetworkPolicy is needed for that network boundary. A proxy policy is not a complete OS sandbox. Shell inherits an allowlisted environment, not all deployment secrets. [Same primary source](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#computers).
- There is also an opt-in local Chrome backend with dedicated profiles and workspace, explicitly not a container/OS network sandbox. [Configuration](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/configuration.md#installed-chrome-for-a-local-api-deployment).
- Native host folder/command access is a separate brokered capability. Tools name explicit grants, are bound to actor/Bot, and include read/write/list and command execution. It depends on a connected native host worker; this is not automatically granted to the web quick start. Broker disconnect revokes grants and fails pending operations. [Host tools](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/host-access/tools.ts#L123-L258), [native worker lease](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/server/src/host-access/broker.ts#L153-L179). Native broker state is in-process Maps, so do not assume persistent host grants from the rest of the product's database persistence.

## Memory and learning

Distinguish saved transcripts, personal factual memory and learned workflow skills.

- Conversations are durable Intelligence threads. Intelligence is required for application startup, not an optional enhancement with a wholly local transcript fallback. [Required configuration](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L147-L171).
- Personal memory can include owner-written, Bot-formed and connected-app-imported facts, with review/provenance and Bot/source restrictions. Entitled Intelligence stores accepted content and ranks recall; OpenBot retains metadata and access restrictions. If the memory feature is unavailable, this particular memory subsystem uses OpenBot tables and later backfills. **That fallback does not remove the separate startup requirement for Intelligence threads.** [Detailed memory contract](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#personal-memory).
- Automatic Learning collects completed conversations into an assigned Intelligence container and delivers published workflow guidance. Learning defaults on, but needs an existing assigned container. Publication is reviewed in Intelligence; enabling analysis does not automatically approve skills. Manually authored slash skills and learned skills do not grant tools. Bring-your-own agents must consume forwarded guidance to benefit. [Learning guide](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/automatic-learning.md).
- Memory source and proactive defaults are enabled for new person/Bot relationships unless disabled. Saved off choices remain off. Data locality must include Intelligence and connected providers, not just the local Postgres database. [Defaults](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L204-L213).

## Integrations

- Governed MCP catalogue includes Google Drive, Gmail/Calendar, Notion, public-web search/fetch and built-in routines. Google/Notion connections are per-user OAuth, separate from administrator enablement and per-Bot grants. Custom MCP servers are supported subject to target checks; Composio optionally brokers a larger app catalogue using a deployment key. [MCP ownership and execution](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#mcp-and-skills), [Composio setup](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L499-L518).
- Gmail and Calendar require administrator-registered Google OAuth client/APIs and each person's connection. Shipping a connector is not equivalent to having the user's account already authorized. The repository includes fake Google for development, ignored in production. [Google setup](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#connect-gmail-and-google-calendar).
- Slack/Teams use an **OpenTag deployment**, shared secret and callback, with `OPENTAG_URL` for outbound messages when no live turn is open. They are not activated simply by starting the web app. SMS uses Twilio; native push uses Expo. [Delivery configuration](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L532-L560).
- Public research supports Parallel, Exa and Firecrawl via MCP, with limited no-key options or operator-paid keys. Admin must enable and grant search/fetch despite the preinstalled skill. The guide explicitly warns that read/search calls can exfiltrate private data in queries or URLs, and recommends a separate research-only Bot. This qualifies the README's broad "checks what leaves" claim. [Research guide and limits](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/web-research.md).

## Supported self-hosting and model choices

The OpenDuet-supported path today is source quick start: Docker, Bun 1.3+, Node/npx, an Intelligence project/key, `bun install`, CopilotKit login/project selection, learning-container helper, model credential and `bash scripts/start.sh`. This research did not perform those steps. The README explicitly says there is **no published OpenDuet image or hosted/deploy guide yet**; bundled Docker/Helm guides deploy plain OpenBot images, not necessarily the OpenDuet product. [Supported setup](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md#quick-start).

Default local configuration is single-user administrator mode. Do not expose it as if it had authenticated multi-user access. Production also needs fresh encryption/tokens, secure origins and appropriate identity configuration. [Single-user boundary](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/.env.example#L61-L72), [security boundaries](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/openbot/docs/architecture.md#security-boundaries).

The committed OpenDuet default is OpenAI `gpt-5.6-terra`. Another OpenAI model is selected in package `model.yaml`, not by `BOT_MODEL` alone. `OPENAI_BASE_URL` allows a compatible gateway or local model, with endpoint/model names passed verbatim. Models need tool support; Responses API-dependent models need an endpoint supporting that API, not just Chat Completions. Anthropic is explicitly documented in OpenDuet quick start, with `BOT_PROVIDER=anthropic`, its key and optional `BOT_MODEL`. Platform configuration additionally supports Google and provider-specific base URLs, and Claude/ChatGPT plan sign-in paths; framework/provider support is not identical across every harness. Intelligence defines one interaction as one successfully completed request from a person, app or scheduled job. Internal model/tool/sub-agent calls are included **for Intelligence metering**, not a promise to pay upstream provider token charges. Follow-up requests count separately; failed requests do not count, and a failed request eventually retried successfully counts once. Development/staging/test/demo usage is listed as free. Spending alerts are informational rather than an automatic stop. Scheduled work and autonomous check-ins can consume the production allowance. [Official pricing FAQ](https://www.copilotkit.ai/pricing).

For a concrete allowance check, a 15-minute routine can produce 96 requests/day, roughly 2,880 in 30 days if all complete. One such routine alone exceeds the 1,000 free hosted allowance. At the default four-hour proactive cadence, a continuously active setting has up to six due checks/day, about 180/month before additional check-in, task and chat turns. These are arithmetic workload illustrations, **not observed billable counts**. Actual completed requests, entitlement and metering need checking in the deployment. Model calls for auxiliary classification, review, summarization and learning can also add inference usage beyond a visible chat answer; the repository does not establish a universal dollar-per-task rate.

Fully local Intelligence is considerably heavier than just Postgres. The official local evaluation guide supports macOS Docker Desktop preview; it accepts Linux rootful Docker but explicitly says Linux runtime evaluation is unverified/outside supported preview. It requires at least 4 CPUs, 12 GiB RAM and 40 GiB free storage **per Intelligence stack**, in addition to other containers. Production Kubernetes deployment requires licensed Intelligence, Postgres, Redis, ingress and OIDC. An official AWS ECS/Fargate route is also linked. [Local evaluation requirements](https://docs.copilotkit.ai/intelligence/self-hosting-local), [production self-hosting](https://docs.copilotkit.ai/intelligence/self-hosting).
